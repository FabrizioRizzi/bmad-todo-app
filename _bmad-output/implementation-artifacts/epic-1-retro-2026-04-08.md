## What Was Challenging

### 1. ⚠️ **Design System Coherence Gap** (Critical Issue)

**What Happened:**
When switching to auto model selection, the AI generated all the CSS variable design tokens (18+ colors, typography, spacing, animation timing) and created components that *used* those tokens—but didn't maintain **visual coherence** across the system.

**Specific Examples:**
- AddInput button implemented as "terracotta" but styling wasn't consistently applied
- TodoCard active state should use `--active-bg` + `--active-bar` but visual hierarchy wasn't fully realized
- Skeleton animations were functional but didn't feel cohesive with the rest of the system

**Why This Happened:**
- Auto model treats requirements as independent checklist items
- Doesn't naturally emerge with unified, coherent visual patterns
- Required more prompting to achieve design system integration

**Impact:** 
- Visual foundation for future epics is inconsistent
- Need to review and standardize component styling before Epic 2
- Future components may not integrate as cleanly

**Where Human Expertise Was Critical:**
- Reviewing components visually against UX specification
- Understanding design coherence as a system property, not individual tokens
- Making trade-off decisions about which visual patterns to standardize

---

### 2. **Complex Requirement Synthesis** (Medium Issue)

**What Happened:**
Stories with multiple interrelated requirements (especially 1.4 and 1.5) were challenging because they required the AI to:
- Hold 20+ constraints in mind simultaneously
- Understand how they interact
- Prioritize which constraints were foundational

**Example:** The design token system (30+ individual definitions) needed to be understood as a unified **system**, not individual tokens. Auto model created them but didn't naturally emerge with elegant integration patterns.

**Impact:**
- Implementations work but lack elegant integration
- Some redundancy in code that Opus 4.6 would have unified

---

### 3. **Type Sharing Across Monorepo** (Low-Medium Issue)

**What Happened:**
Frontend needed to match backend's Todo type definition, but types were duplicated:
- Backend: Drizzle/Zod types
- Frontend: Manual TypeScript type definitions

**Why This Was Limiting:**
- Type changes in backend require manual updates in frontend
- No single source of truth
- Future maintenance burden

**Where Human Expertise Was Critical:**
- Architectural decision: Should types be generated from OpenAPI spec?
- Monorepo strategy for shared types

**Status:** Works acceptably for MVP but should be addressed in Epic 2 prep.

---

### 4. **Performance & Optimization** (Low Issue)

**What Happened:**
Code was functional but not optimized:
- No analysis of bundle size impact
- Components could benefit from React.memo but AI didn't suggest it
- TanStack Query keys were basic (just `['todos']`)

**Where Human Expertise Was Critical:**
- Decisions about when to optimize vs. when to keep simple

**Status:** Adequate for MVP; should be revisited in Epic 3-4.

## Key Insights & Learnings

### Learning #1: Model Selection is Critical for Design-Heavy Work

**The Core Issue:**
- **Opus 4.6:** Maintained visual design system coherence, anticipated integration points, proposed elegant unified solutions
- **Auto Model:** Completed requirements one by one, treated design system as individual checklist items, lacked polish

**Implication:** For UI-heavy epics, faster models create technical debt in the visual/interaction layer that's harder to fix later.

**Action:** Use Opus 4.6+ for design-heavy stories going forward.

---

### Learning #2: Design Systems Aren't Just Collections of Tokens

**The Core Insight:**
A design system is a **unified whole** where each component reinforces the others. Fast AI models treat them as independent specifications.

**Example:** 30 individual color/spacing/animation tokens need to be *understood as a system* for the AI to apply them coherently across components.

**Action:** Create `DESIGN_SYSTEM.md` with examples of how tokens work together. Update prompts to explicitly ask for system coherence.

---

### Learning #3: Prompting Matters More Than We Thought

**The Core Insight:**
Prompting requirements separately leads to fragmented solutions. Unified prompts with all constraints lead to elegant integration.

**Example:**
- ❌ "Create design tokens. Now create components that use them."
- ✅ "Create an integrated design system where tokens define component appearance and all components express the same visual language"

**Action:** Develop unified prompt templates for complex requirements.
