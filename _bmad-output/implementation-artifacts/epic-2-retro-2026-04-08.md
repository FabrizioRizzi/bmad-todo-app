### 1. **Sophisticated Undo Mechanism Delivered with High Quality**

**Story 2.2 (Delete with Undo) was technically complex:**
- Optimistic card removal with slide animation
- 5-second grace period with visual countdown
- Undo button restores card mid-grace period without API call
- Timer expiry fires DELETE endpoint
- API failure during grace period restores card
- Multiple concurrent deletes handled correctly (new delete flushes pending delete's API call)

**How the team handled it:**
- Used Claude 4.6 Opus model (learned from Epic 1) → more elegant solution
- Comprehensive code review caught 11 critical/medium issues:
  - Race conditions between timers
  - Memory leaks from uncleaned-up setTimeouts
  - Stale snapshots on undo (documented as acceptable limitation)
  - Visual/API timer drift
  - Duplicate row restoration logic
  - Socket/animation race conditions
- All issues fixed before merge
- Post-review, 0 regressions in E2E tests

**Impact:** The team proved it can handle stateful interactions with maturity. This builds confidence for future epics.

## What Was Challenging

### 1. **Stateful Interaction Complexity** (High Impact)

**The Challenge:**
Delete/Undo (Story 2.2) required managing multiple intertwined state machines:
- Optimistic update state (card removed from list immediately)
- Timer state (5-second countdown to API call)
- API state (DELETE in-flight, pending, success, error)
- Visual state (card slide animation, toast animation)
- Undo state (restore flow if user clicks within window)

**Specific Complications:**
- **Timer/API Drift:** Visual countdown timer vs. actual API commit timer could drift if user navigates/minimizes tab
- **Race Conditions:** Multiple deletes could trigger duplicate API calls if not carefully managed
- **Stale Snapshots:** Undo restores a snapshot from delete-click time; concurrent edits would be lost (acceptable but documented)
- **Memory Leaks:** clearTimeout() calls easy to miss if error recovery paths don't clean up

**How the Team Addressed It:**
- Code review discipline: 11 patches identified and applied post-review
- Defensive programming: Added guards for NaN date comparisons, checked for duplicate rows
- Testing strategy: Unit tests found logic bugs, code review found architectural issues, E2E tests validated user journeys

**Learning:** Stateful interactions need multiple validation layers. Tests catch implementation; code review catches architecture.

---

### 2. **UX Complexity Underestimated** (Medium Impact)

**What Seemed Simple:** "Add delete button and DELETE endpoint"

**What Was Actually Needed:**
- Delete button visibility logic (desktop: hidden, hover to reveal; mobile: always visible, 50% opacity)
- 5-second undo window (why 5 seconds? Not 3? Not 10?)
- Toast position, animation timing, dismissal (manual or automatic)
- Multiple concurrent deletes (what happens if user deletes twice while first undo is pending?)
- Visual feedback during pending delete (disabled state, animation class)

**Where the Complexity Came From:**
- Alice (Product Owner) had to clarify UX decisions mid-epic
- Story acceptance criteria captured these details, but weren't fully visible until implementation

**Learning:** UX complexity often hidden in acceptance criteria. Bringing UX specialist into dev discussions earlier reduces surprises.

---

### 3. **Error State Management Refactor** (Medium Impact)

**The Challenge:**
Story 2.3 required consolidating error handling:
- Pre-epic: Error messages in TodoList (for delete), in AddInput (for create), in TodoCard (for toggle)
- Challenge: Each component had different error message patterns, different dismiss logic
- Solution: Centralize in App component with action-specific messages

**Why It Was Challenging:**
- Required understanding data flow from all three mutation points to centralized error state
- Required changing component interfaces (adding onError callbacks)
- Risk: Refactoring error handling could introduce bugs while features are still in use

**How the Team Addressed It:**
- Elena (Junior Dev) worked through the refactoring methodically
- Tests validated that each mutation still showed correct error message
- No production incidents (features only used internally during dev)

**Learning:** Architectural refactors easier when done early. Every new story brings opportunity to improve architecture.

---

### 4. **Timing-Dependent Testing Gaps** (Low Impact)

**The Gap:**
Most testing frameworks can verify logic, but timing is harder:
- Unit tests use mocked timers (good for deterministic testing)
- E2E tests use real timers (but timing flakiness possible)
- Manual testing proved visual timer matched API commit timer (code review found drift, fixed it)

**Examples of Issues Timing Tests Didn't Catch:**
- Visual countdown timer drift from actual API commit (caught by code review)
- Toast auto-dismiss timing not matching 8-second spec (caught by manual testing)
- Animation timing misalignment with state transitions (caught by visual review)

**Learning:** Timing-dependent features benefit from specialized test frameworks (e.g., animation snapshot testing) or dedicated timing verification during code review.

## Key Patterns & Learnings

### Learning #1: Model Selection is a Strategic Decision

**The Pattern:**
Different story types benefit from different models:
- **Straightforward features (Story 2.1):** Haiku sufficient, fewer iterations
- **Stateful/architectural work (Story 2.2, 2.3):** Opus produces more elegant, far-thinking solutions
- **Performance improvement:** Consider specialist models if available

**Decision Framework:**
| Story Type | Model | Rationale |
|-----------|-------|-----------|
| Straightforward CRUD endpoint | Haiku | Sufficient capability, faster/cheaper |
| UI feature with simple interactions | Haiku | Clear requirements lead to clean implementation |
| Stateful/complex interactions | Opus | Anticipates edge cases, proposes elegant solutions |
| Architectural decisions | Opus | Understands system implications, proposes coherent designs |
| Performance/optimization | Specialist | Requires deep knowledge of optimization techniques |

**Action:** Document this framework in project guidelines for future epic planning.

---

### Learning #2: Code Review is Specialized for Stateful Code

**The Pattern:**
Story 2.2 code review identified 11 issues that tests missed:
- Race conditions between timers
- Memory leak cleanup paths
- Stale snapshot assumptions
- Edge cases in concurrent scenarios

**What Made Code Review Effective:**
- Dedicated time for security/edge case analysis (not just style checking)
- Multiple reviewers with different expertise (senior dev for architecture, QA for timing logic)
- Specific checklist for stateful components (timer cleanup, ref management, cache invalidation)

**Checklist for Stateful Components:**
- [ ] All timers/intervals have matching clearTimeout/clearInterval calls
- [ ] Cleanup logic in useEffect dependencies covers all timers
- [ ] Race conditions prevented when state updates from multiple sources
- [ ] Optimistic updates properly reverted on error
- [ ] Cache invalidation doesn't cause duplicate data
- [ ] Edge cases tested: concurrent mutations, network failure, user cancel
- [ ] Accessibility maintained through state transitions

**Action:** Formalize stateful component code review checklist.
