## Epic summary

All three stories reached **done** with unit, integration, and targeted E2E coverage. Epic 3 extended the API (optional `dueDate`, richer PATCH semantics), added Shadcn-style calendar UX, and layered client-only filter and sort with motion and accessibility requirements.

---

## What went well

- **Clear pipeline in the UI:** Filter → sort → list reads naturally in code and matched architecture notes (`app.tsx` owns filter/sort state; no spurious API calls).
- **Story 3.1 backend design:** Optional `dueDate` on POST, PATCH accepting partial updates with `superRefine` (reject `{}`), and dynamic Drizzle `set` kept the API flexible without breaking existing toggle behavior.
- **Date handling discipline:** ISO date strings (`YYYY-MM-DD`) end-to-end reduced timezone surprises; utilities (`formatDueDate`, `isOverdue`, sort helpers) stayed testable in isolation.
- **Code review on 3.1:** Caught overlapping PATCH while popover open, malformed ISO edge cases, and screen-reader labeling on AddInput—fixed before calling the story truly done.
- **Story 3.2 animation UX:** Render-time exiting/entering IDs and “exiting rows first” ordering avoided the Active↔Completed height jump; shows attention to perceived performance and layout stability.
- **Story 3.3 complexity managed:** FLIP-style reorder with `sortLayoutKey` and brief filter FLIP suppression prevented animation fights between filter and sort; spec decisions (D1/D2) were recorded in the story file.
- **Test layering:** Co-located component tests plus `e2e/story-3.3-sort-todos.spec.ts` (and related flows) gave confidence for regressions on toolbar semantics and ordering.

---

## What was challenging

- **Shadcn / calendar stack:** CLI and pnpm store friction led to hand-written `calendar`/`popover` wiring (`react-day-picker` v9, design tokens)—more integration work than a “drop in component” story.
- **Concurrent mutations (3.1):** Due-date PATCH from an open popover needed explicit disabling and guards—similar class of problem to Epic 2 timers, but in a different UI shape.
- **Combined motion (3.2 + 3.3):** Filter height/opacity transitions plus sort reorder transforms required careful coordination; FLIP implementation is powerful but sensitive to future DOM changes (called out as deferred risk in 3.3 review).
- **Spec drift vs shipped UI (3.3):** Default labels, due-direction toggle, and reset-sort behavior needed explicit product decisions (D1) and doc updates—good outcome, but a reminder to align AC early when UX is dense.
- **Data assumptions:** Sort relies on valid ISO date strings; malformed data would sort oddly—acceptable given API validation, but shared with Epic 2’s “defensive guards” theme.

---

## Learnings (carry forward)

1. **Partial PATCH pattern:** Reusable pattern for future fields—keep “at least one field” validation and dynamic `set` objects consistent across routes.
2. **Animation specs:** When multiple animations interact (filter + sort + delete), document interaction order and add a short “animation contract” in Dev Notes or architecture to avoid rework.
3. **Review focus for popover/edit flows:** Always test in-flight mutation + disabled UI + queued actions; mirrors Epic 2’s stateful-component checklist.
4. **E2E for spatial UX:** Sort order and toolbar visibility under filter changes are faster to lock with Playwright than with unit tests alone—keep E2E narrow but high-signal.
5. **Demo seed:** `db:seed:demo` improved manual and MCP-assisted QA; keep dev-only seeds scoped and documented (D2-style decisions).
